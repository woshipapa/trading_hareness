## 两个起点的行为

- 空库或 peer sep0002：ow0120 先比对实际定义，再补缺对象。已有同名错误定义直接失败，
  仅上述已审核的旧盘口索引例外。普通索引使用 CONCURRENTLY；主键和唯一约束由约束管理。
- owner 0119：只执行 ow0121。它读取 pg_catalog 验证必需对象及定义，不执行 DDL、修复或 LOCK。
  出现差异时停止，不在维护窗口里自动扩大修复范围。
- 多出的共享对象不会让验证失败；物理表空间、所有者、ACL 和运维 reloptions 不作为逻辑差异。
- 两个新迁移只支持向前演进，downgrade 明确拒绝删除历史证据结构。
- 新库须使用仓库的 `database_bootstrap.py` 初始化冻结基线；不能跳过既有 bootstrap 契约。

冻结合同目前覆盖 223 个关系、2,600 列、798 约束、556 索引、4 函数、17 触发器、12 序列。
索引的 valid/ready 状态也检查，不能把 IF NOT EXISTS 或同名对象当成验收证明。
种子、来源启停、角色权限、策略权重另行验收；结构一致不会自动开启策略或修改运行配置。

## 唯一迁移执行方及窗口

1. 维护方合并后，两端先采用同一套 0118、0119、ow0120、ow0121、辅助模块及 JSON 合同，
   同时确认 sep0001 → sep0002 原始链已恢复；逐文件摘要一致后才能升共享库。
2. Windows 已在独立待发布源码中采用相同文件；当前在线旧版本未切换。
   正式窗口开始前必须让所有 Windows 发布、启动和定时路径停止执行 Alembic。
   维护方执行之前必须获得该状态的明确确认，不能把本地准备等同于线上协同完成。
3. 本次只由维护方正式发布执行共享库迁移；Windows 不执行 upgrade、stamp 或 downgrade。
4. 迁移后维护方读回 head、必需结构、服务状态，再通知 Windows 切换已准备源码。
   迁移后禁止恢复不认识 ow0121 的旧发布目录，也不得用旧版重启路径启动服务。
5. 双方验收完成后才移除外来 revision 放行。维护窗口须另行通知和确认。
