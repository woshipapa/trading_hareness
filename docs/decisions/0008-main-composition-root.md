# 0008 拆分 main.py：运行时上下文与按领域的装配模块

- 状态：生效（进行中）
- 日期：2026-10-09

## 背景

`quant-service/app/main.py` 有 6,671 行、480 个顶层函数（2026-10-09 测量），并从约 290 个
模块导入。它不只是装配根：480 个函数里有 354 个直接或间接读写模块级状态，包括 `db`、
`async_db`、`run_database_blocking`、各类缓存和运行时对象。只有 126 个是纯函数，合计 867 行，
而且大多是几行长的转发。

拆分的真正阻力在测试：33 个测试模块对 `app.main` 打了 209 处补丁，其中仅
`run_database_blocking` 就有 52 处。函数一搬走，这些补丁就落空，测试会静默地测到真实依赖。

## 决定

- 新建运行时上下文（db、async_db、阻塞执行器、HTTP 客户端、缓存），由 main 创建一次。
- 每个领域一个装配模块，接收上下文，组装该领域的服务依赖、路由和后台任务。main.py 最终
  只负责创建上下文、调用各装配模块、挂载路由、启动后台任务。
- 测试改为替换上下文或装配模块里的依赖，不再对 `app.main` 打补丁。每迁移一个领域，就同时
  迁移它的测试补丁。
- 顺序按测试耦合从低到高：集合竞价脉冲 → 老师复盘 → 小杰 → 板块资金流 → 全市场快照 →
  盘后 → 盘中扫描（最后）。
- 不重写业务逻辑，只搬运和装配；每一步都由全量测试证明行为不变。

## 后果

迁移期间两种写法并存。`scripts/verify_architecture.py` 给 main.py 设了只降不升的上限
（`MAIN_MAX_LINES`、`MAIN_MAX_FUNCTIONS`）：任何让它变大的提交都会让 CI 失败，每次拆分在同一个
提交里调低上限。目标是 400 行以内、导入的模块不超过 40 个。

## 怎样保证

架构检查里的上限；"main.py 不直接读环境变量"由 `tests/test_settings.py` 守住（配置已集中到
`app/settings.py`）；"main.py 不直接定义 HTTP 路由"由架构检查守住。

实际做法与上面的"决定"有两处差别，如实记在这里：

- 还没有建统一的运行时上下文。每个领域用自己的依赖数据类（`…Dependencies`），main.py 里用
  延迟绑定的 lambda 组装，所以测试对 `app.main` 打的补丁仍然有效。这让搬运可以一步一步做、
  每步都能用原测试证明行为不变，代价是测试补丁还没迁走（190 处）。
- 导入的模块数不降反升：每搬出一个模块，main.py 就多一行导入。函数和行数在降，扇出要靠下一步。

下一步：

1. 按领域建装配模块（`app/assembly/<领域>.py`），把该领域的依赖数据类、路由构建和后台任务
   注册连同它们的导入一起搬过去。main.py 现在有 789 行导入、209 行 `include_router` 装配，
   这一步是行数降到 400 以内、扇出降到 40 以内的主要来源。
2. 迁移测试补丁：装配模块落地一个，就把对应测试从 `patch("app.main.X")` 改为替换该领域的依赖。
3. 剩余领域：全市场日线与板块/概念同步（等 0005 里 Tushare 替代来源的决定后再搬，否则是在
   搬即将删除的代码）、盘后编排、盘中扫描（最后）。
