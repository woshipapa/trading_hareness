# 爱投顾内参自动化笔记

> 目标：不用每次在微信里点开「爱投顾」公众号的内参，自动拉取「尾盘掘金内参 / 猎场擒龙内参」的更新正文，推送到飞书群。
> 生成日期 2026-09-01。涉及两个仓库：本仓库 `wechat-export-macos`（token 捕获 + 手动工具）与 `~/codebase/n8n`（监听器 + 部署）。

---

## 0. 一句话结论

内参正文在 `group-api.itougu.com` 的 H5 后端，鉴权是**长效 Authorization bearer（JRJ+JWT，约 1 年）**、不落盘。
通过「Clash TUN 层临时把 itougu 引到 mitmproxy」抓到一次 token，之后就能直接调 API 拉正文。
当前两层监听：**本地专表监听（~秒级，事件驱动）** + **远端 47 定时轮询（A股时段每 15s，兜底）**，都发到飞书「公众号同步群」。

---

## 1. Token 捕获完整流程

### 1.1 为什么必须抓包
- 内参 H5（`group-app.itougu.com`）只是前端壳，数据接口在 `group-api.itougu.com`。
- 鉴权不是 cookie，而是请求头 **`Authorization: JRJ<jwt>`** + `TempId` + `DeviceInfo`。
- 翻遍微信 XWeb（内核代号 **radium**）全部 6 个 webview profile 的 Cookies / LocalStorage / IndexedDB / SessionStorage，`itougu` 零命中 →
  **结论：token 不落盘**，是每次打开页面时微信 OAuth 现换、只存在内存里。所以静态抠不出来，只能抓一次真实请求。

### 1.2 抓包为什么一波三折（关键坑）
1. 起 mitmproxy + 设系统代理 → **抓不到**。诊断：微信（含网页进程 `WeChatAppEx Helper`）连接源地址是 `198.18.0.1`（Clash 的 **TUN 网卡**），
   即微信流量在 IP 层被 Clash TUN 接管，**完全无视 macOS 系统代理**。
2. 解决：在 Clash（verge-mihomo）临时加规则，把 itougu 引流到 mitmproxy：
   - `proxies` 加 `mitm`（http, 127.0.0.1:8080）
   - `rules` 顶部：`PROCESS-NAME,mitmweb/mitmdump/mitmproxy,DIRECT`（**防回环**，让 mitmproxy 自己出站直连）+ `DOMAIN-SUFFIX,itougu.com,mitm`
   - `find-process-mode: always`（PROCESS-NAME 规则才生效）
   - 改 runtime `clash-verge.yaml` + 全局 `profiles/Merge.yaml`（持久化，扛 Verge 重刷），经 unix socket `/tmp/verge/verge-mihomo.sock` `PUT /configs` 热重载。
3. 又一坑：微信对 `group-api` 用的是**很早建立、一直复用的 HTTP/2 长连接**，规则加上后老连接仍走旧路由 →
   用 `DELETE /connections/:id` 掐断 itougu 连接 + **彻底关掉内参页再重开**，逼它建新连接走 mitm。
4. 在微信里点开内参 → mitmproxy 插件 `itougu_capture.py` 抓到全套请求头写 `itougu_auth.json`，顺带把响应存 `captured/`。
5. 收尾：**还原 Clash 配置**（否则 mitmproxy 一停 itougu 打不开）、关系统代理、停 mitmproxy。（安全）不再抓包时删 mitmproxy CA：
   `security delete-certificate -c mitmproxy ~/Library/Keychains/login.keychain-db`

### 1.3 抓到的凭据
- `Authorization: JRJ<JWT>`，JWT `exp = 2027-09-01`，**有效期约 1 年**。
- 同时需要 `TempId`、`DeviceInfo`（每会话独有；缺了会 502 / 系统异常）。全部存在 `itougu_auth.json`（已 gitignore）。

### 1.4 接口契约（逆向前端 bundle + 抓包联合确定）
- 域名：`https://group-api.itougu.com`
- 内参路径前缀 **`/teach-product/internalReference/`**（圈子/文章类是 `/teach-community/`）
- **方法 POST + JSON body `{"businessProductId":"<id>"}`**，成功码 **`code == 20000`**
- `/user/getInfoById` → 元信息（productName、isBuy、daysRemaining、consultants…）
- `/appendContent/list` → 正文，`data.listResult[]`，每条含：
  - `content`（HTML 正文）、`publishTime`/`createTime`、`consultantName`、`tipContent`
  - `stockTransactionDetail` / `simulateOperationJson`：`{stockName, stockCode, mkt, price, position, dealType}`
    - **`dealType`：0 = 买入/加仓，1 = 卖出/离场**；`price` 价位；`position` 仓位份数
  - `reportList[]`：研报（orgName、emRatingName、title、filePath PDF）

### 1.5 目标内参（productId = 微信推送里的 businessProductId）
| 内参 | businessProductId |
|---|---|
| 尾盘掘金内参 | `1806593447818383361` |
| 猎场擒龙内参 | `1661993558510538753` |

是 **type-49** 卡片，URL 里带 `productId`。

## 2. 当前工作流架构

```
                        ┌───────────────────────── 本地 Mac ─────────────────────────┐
爱投顾推送"内参有更新"  →  写入 biz_message_0.db（秒级实时）
（微信服务器）              │
                          │  ① itougu-table-watch（supervisor daemon，主链路，~秒级）
                          │     只解密 biz 库一次 + 每 1.5s 应用 WAL 增量、只读爱投顾一张表
                          │     看到内参卡片 → trigger_from_push → 调 itougu API 拉正文
                          └──────────────┬───────────────────────────────────────────┘
                                         │                          直连 itougu API（不看微信库）
                        ┌── 远端 47 ─────┴──┐   ② itougu-neican.service（systemd，兜底）
                        │  A股 9:30-11:30 /  │      每 15s POST appendContent/list，有新增就发
                        │  13:00-15:00       │
                        └────────┬───────────┘
                                 ▼
                        飞书「公众号同步群」 oc_570aeb3bbfb11fa2be66b25ca4568aad
```

### 2.1 脚本清单
**本仓库 `wechat-export-macos/`（token 捕获 + 手动工具）**
| 文件 | 作用 |
|---|---|
| `itougu_capture.py` | mitmproxy 插件：微信点内参→抓 token 写 `itougu_auth.json` |
| `itougu_fetch.py` | 用 token 手动拉内参正文（`--md` / `--json` / `--raw` / `--product`） |
| `itougu_feed.py` | 从本地库看两个内参何时有更新+链接（无需凭据） |
| `itougu_auth.json` | 抓到的 token 全套请求头（**gitignore**） |

**`~/codebase/n8n/scripts/`（自动监听 + 发飞书）**
| 文件 | 作用 |
|---|---|
| `itougu_neican_relay.py` | 核心中继：拉增量 + 解析（含交易明细/研报）+ 发飞书 + 去重。`trigger_from_push`（供专表监听调用）、`--loop/--once/--bootstrap`、`ensure_baseline`（首启自动建基线）。路径全走环境变量。 |
| `itougu_table_watch.py` | 本地专表低延迟监听（decrypt base 一次 + WAL 增量 + 只读爱投顾表） |

### 2.2 两层触发
- **主：本地专表监听** `itougu-table-watch`（supervisor daemon）。微信秒级写库 → 1.5s 扫描 → ~秒级触发。**实测真实自动推送端到端 ≈ 17 秒**。
- **兜底：远端轮询** `itougu-neican.service`（47 上 systemd）。A股交易时段每 15s 直连 itougu，与微信库无关，防漏。
- **去重两层**：各自本地 state（记已发 `appendContentId`）+ 飞书 `uuid5(appendContentId+chat_id)` 幂等 → 本地与远端重叠**不会重复发**。

### 2.3 关键实测数据（打消"库不实时"的担心）
- 微信写库**秒级实时**：`biz_message_0.db-wal` mtime 紧跟消息；凌晨公众号消息落库滞后仅 28-70s（主要是 relay 扫描节奏，非微信写慢）。
- `biz_message` 整库解密 `decrypt_base` ≈ 3.7s、`apply_wal` ≈ 0.01s → 所以专表监听只解一次 base、之后只应用 WAL。
- itougu API **10s 间隔 × 30 次、5 分钟、0 风控**（http 200/code 20000，延迟 258-507ms）→ 采用 15s 更稳。

## 3. 部署与运维

### 3.1 本地（supervisor 统一 venv `~/.venvs/svc/bin/python`）
- `itougu-table-watch` 是 `svc_supervisor.py` 的一个 daemon task。
- 改脚本/supervisor 后重载：`launchctl kickstart -k gui/$(id -u)/com.papa.svc-supervisor`
- 快照文件：`n8n/state/itougu-table.snapshot.db`（专表）、`wechat-biz.snapshot.db`（biz-relay），各 ~363MB。

### 3.2 远端 47（47.114.113.152，照 quant-intraday-edge 范式）
- 服务：`/etc/systemd/system/itougu-neican.service`，`ExecStart=python3 itougu_neican_relay.py --loop --interval 15 --trading-hours-only`
- 目录：`/opt/itougu-neican/`（脚本 + `itougu_auth.json`，600）；状态 `/var/lib/itougu-neican/state.json`
- 配置：`/etc/itougu-neican.env`（600，飞书凭据 + itougu 配置）
- 部署产物：`n8n/deploy/itougu-neican/`（unit + env.example + README）
- 常用：
  ```bash
  ssh -i ~/.ssh/feishu_relay_edge_ed25519 root@47.114.113.152
  systemctl status itougu-neican
  journalctl -u itougu-neican -f          # 盘中看推送
  systemctl restart itougu-neican         # 改 env 后
  ```

### 3.3 Token 过期（约 1 年后 / 报 "token 失效"）
1. 本地重跑抓包：起 `itougu_capture.py`（mitmproxy）→ Clash 临时引流 → 微信点开内参 → 新 `itougu_auth.json`
2. 覆盖远端：`scp itougu_auth.json root@47.114.113.152:/opt/itougu-neican/itougu_auth.json`
3. `ssh … 'systemctl restart itougu-neican'`；本地专表监听会自动用新的（下次调用即生效）

### 3.4 可调项
- 交易时段 / 间隔 / 目标飞书群：远端在 `/etc/itougu-neican.env` 与 unit；本地在脚本 `WATCH` / `CHAT_IDS`。
- 新增要监听的内参：把 businessProductId 加进 `itougu_neican_relay.py` 的 `WATCH`。

## 4. 安全备注
- `itougu_auth.json`（含 token）已 gitignore；远端为 600。
- 抓包给系统信任过 mitmproxy CA，不再抓包时应删除（见 §1.2）。
- 飞书凭据复用 feishu-relay-edge 那个飞书应用；本地 `n8n/.env`、远端 `/etc/itougu-neican.env`，均不入库、不打印。
